# 后端部署 / 运维手册

目标环境：阿里云 CentOS 服务器，进程由 `supervisorctl` 管理。

> 想用 Docker 部署（不装 `uv`/`supervisor`，交给容器管理）？见
> [Docker部署.md](Docker部署.md)，两条路径二选一即可。

## 为什么不能直接搬本机的 Python 环境过去

`uv.lock` 锁定的 `uvicorn[standard]` 依赖里，`uvloop`/`httptools` 是编译好的二进制，
Windows 上装的和 CentOS x86_64 上装的不是同一份文件，跨平台搬 `.venv` 装不上/跑不起来。

正确做法：把**代码 + 锁文件**（`pyproject.toml` + `uv.lock`）搬到服务器上，用 `uv` 在服
务器上现场装出一套隔离的 Python 环境（`uv` 会自己下载匹配的 Python 3.10，不依赖 CentOS
自带的老 Python）。这套环境就在 `backend/.venv/` 里，和系统 Python 完全隔离——效果上等
同于"把 Python 环境打进了包里"，只是这个动作发生在目标机器上，不是在本机打包传过去。

不需要额外生成 `requirements.txt`：`pyproject.toml` + `uv.lock` 本身就是比它更精确的依
赖清单（连版本哈希都锁了）。

## 一、服务器一次性准备

```bash
# 装 uv（不需要 root，装用户目录下即可）
curl -LsSf https://astral.sh/uv/install.sh | sh

# 如果服务器到 pypi.org 很慢/超时，配个国内镜像
export UV_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/
# 如果连下载 Python 解释器本体也很慢，再配一下（写进 ~/.bashrc 长期生效）
# export UV_PYTHON_INSTALL_MIRROR=<国内镜像地址>

# 装 supervisor（如果还没有）
yum install -y supervisor
systemctl enable --now supervisord
```

## 二、部署代码（首次）

```bash
git clone <repo地址> /opt/kb-backend    # 之后更新用 git pull
cd /opt/kb-backend/backend
cp .env.example .env
vim .env                       # 填生产库的 DB_HOST/DB_USER/DB_PASSWORD 等
uv sync --frozen               # 按 uv.lock 精确还原依赖，产出 .venv/
uv run alembic upgrade head    # 建表/迁移
```

> `.env` 的加载路径是相对 `config.py` 文件位置算的，不是相对当前工作目录——只要 `.env`
> 放在 `/opt/kb-backend/backend/.env`，supervisor 不管从哪个目录拉起进程都能读到，不需
> 要在 supervisor 配置里额外传环境变量。

## 三、配置 supervisor

模板见 [deploy/kb-backend.supervisor.ini.example](deploy/kb-backend.supervisor.ini.example)，
`command` 直接指向 `.venv` 里的 uvicorn 二进制（它的 shebang 已经绑定了 `uv sync` 产出的
那个隔离解释器+依赖），supervisor 进程本身不需要认识 `uv`、不需要激活任何 venv。

```bash
mkdir -p /var/log/kb-backend
cp deploy/kb-backend.supervisor.ini.example /etc/supervisord.d/kb-backend.ini
# 改里面的 directory / command 路径、user 字段
supervisorctl reread
supervisorctl update
supervisorctl status kb-backend
```

## 四、更新代码（日常运维流程）

```bash
cd /opt/kb-backend && git pull
cd backend && uv sync --frozen && uv run alembic upgrade head
supervisorctl restart kb-backend
```

## 五、服务器完全无外网出口时怎么办

上面的流程假定服务器能访问 PyPI（或镜像）。如果安全策略完全禁止外网出口，就没法在目标
机器上现场 `uv sync`，只能换思路：

1. 找一台架构/系统与目标一致的机器（同为 x86_64 CentOS，glibc 版本兼容）。
2. 在那台机器上 `uv sync --frozen` 一次，产出完整的 `.venv/`。
3. 把整个 `.venv/` 打成 tar 包，连同代码一起传到目标服务器解压。

这种情况下才是真的"打包 Python 环境"传过去，而不是在目标机器上现场装——仅在完全无网络
出口时才需要，日常部署走前面四步即可。

## 六、挂在 `/kb-api` 子路径下（platform-enterprise.yicall.com）

正式环境不是直接把 8000 端口暴露给公网，而是跟前端共用同一台服务器上的 nginx，走
`https://platform-enterprise.yicall.com/kb-api/...` 这个子路径进来。nginx 那边（网关自
己维护，不在这个仓库里）现有的配置大致是：

```nginx
location /kb-api {
    client_max_body_size 50m;
    proxy_set_header Host $proxy_host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_pass  http://127.0.0.1:8000/;
    proxy_connect_timeout 5s;
    proxy_read_timeout 1200;
}
```

**关键点：`location /kb-api` 配 `proxy_pass http://127.0.0.1:8000/`（带尾部 `/`），nginx
会把请求路径里匹配到的 `/kb-api` 前缀原样剥掉再转发**——比如浏览器请求
`/kb-api/health`，backend 实际收到的是 `/health`。所以：

- **后端代码不需要知道 `/kb-api` 这个前缀的存在**，路由该怎么写还是怎么写（`/health`、
  `/knowledge-bases` 等），不需要挂 FastAPI 的 `root_path` 或者给路由加前缀。
- `deploy/kb-backend.supervisor.ini.example` 里的 `command` 已经把 `--host` 从
  `0.0.0.0` 改成了 `127.0.0.1`——只监听本机，不再对公网暴露 8000。因为公开入口现在是
  nginx 的 443/80，8000 只需要给同一台机器上的 nginx 连，不需要（也不应该）再让公网直
  接访问；如果阿里云安全组之前为了调试开了 8000 的公网入站规则，这次可以顺手收掉。改完
  记得 `supervisorctl restart kb-backend` 让新的 `--host` 生效。
- **CORS 基本不再是问题**：浏览器发请求判断"是不是跨域"看的是 scheme+host+port（不看路
  径），前端跑在 `https://platform-enterprise.yicall.com/kb-web/...`、接口打到
  `https://platform-enterprise.yicall.com/kb-api/...`，两者 origin 完全一样，浏览器根本
  不会当成跨域请求，不会带 CORS 预检。`.env.example` 里仍然把这个域名加进了
  `CORS_ALLOWED_ORIGINS`，纯粹是给"直连后端调试"这种绕开网关的场景留个后路，正式流量走
  网关不依赖这条配置。
