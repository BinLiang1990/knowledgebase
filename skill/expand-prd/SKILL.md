# /expand-prd — 用工程思维给 PRD 找漏洞并补全

`requirement-analyst` 负责从零采集需求；这个 skill 负责在需求已经写下来之后，
以工程师的视角挑漏洞——很多产品视角的需求描述只覆盖了"主路径"，
漏掉了闭环里配套的输入/输出、CRUD、异常、权限等环节。

参数（`$ARGUMENTS`）：
- 空：审查整份 `docs/PRD.md`
- 一个数字或需求名（如 `3` 或 `需求 3`）：只审查这一条需求
- 一个路径：审查该路径下的 PRD 文件

---

## 工作流程

### 1. 读取目标 PRD

默认读 `docs/PRD.md`；`$ARGUMENTS` 给了路径就读那个文件。如果文件不存在，
告诉用户并停止——不要凭空生成 PRD，这不是这个 skill 的职责。

### 2. 逐条需求过一遍"工程闭环检查表"

对 PRD 里的**每一条**需求（或 `$ARGUMENTS` 指定的那一条），依次用下面 10 个
维度检查描述和验收标准有没有覆盖到。不是每条需求都会命中每个维度——只记录
**真正适用且缺失**的项，不要为了凑数量硬套。

| 维度 | 检查问题 | 典型遗漏例子 |
|---|---|---|
| **输入对称性** | 用户被要求提供结构化输入（上传文件/填表单）时，系统是否告诉过用户"该输入什么"？ | 要求上传 CSV，但没有模板下载、没有字段说明 |
| **输出可见性** | 数据被创建/导入/生成之后，有没有地方能让用户看到它、确认它进去了？ | 导入了企业数据，但没有企业列表页 |
| **CRUD 闭环** | 创建之后能不能改、删、批量操作？ | 能导入企业，但导入错了没法删除/重新导入 |
| **状态与生命周期** | 重复操作（如再传一次 CSV）会怎样：覆盖、追加、去重、报错？有没有版本/历史？ | 两次导入同名企业，行为未定义 |
| **异常与边界** | 部分失败、空状态、超大输入、极端值有没有交代？ | 已覆盖部分行失败，但没说"0 条有效数据"时怎样 |
| **权限与审计** | 谁能做这个操作？有没有留痕（谁在什么时候做了什么）？ | 导入操作无操作人/时间记录 |
| **性能与规模** | 数据量变大（10 条 vs 10 万条）时，交互方式是否还成立？要不要分页/异步/进度条？ | 验收标准只测了 10 条，量级到万条时同步导入会超时 |
| **依赖一致性** | 这条需求产出的数据，是否满足下游需求（其它"需求 N"）真正需要的字段/形态？ | 需求 3 导入的字段少了需求 4 匹配要用的字段 |
| **反馈与通知** | 耗时操作/失败结果，用户如何被告知？是否需要之外的入口再看一次结果？ | 导入完成提示一闪而过，没地方回看"上次导入了什么" |
| **非功能边界** | 文件类型/大小限制、注入风险（如 CSV 公式注入）、敏感字段脱敏，是否需要写明？ | CSV 导入未限制文件大小/类型 |

### 3. 每条需求整理成三段输出（先讲给用户，不要直接改文件）

对每条被检查出问题的需求：

```
### 需求 N：<名称> — 发现的缺口

- **缺口 1**：<用一句话说清楚缺什么，套用检查表里的维度>
  - 建议：新增验收标准 / 新增子需求 / 修改描述（挑一种，给出具体文案）
- **缺口 2**：...
```

建议的文案要能直接套进 PRD 现有格式：
- 如果是补验收标准，用现有的 `当……时，应……` 格式，接在原需求的验收标准列表里。
- 如果缺口大到需要独立需求（比如"模板下载"值得单独验收），提议新增一条
  `需求 N.1` 或紧邻插入的新编号需求，带完整的 描述 + 验收标准。
- 不要发明业务规则（比如具体的重复数据处理策略）——如果这类判断只有产品/用户
  能拍板，在建议里用 `[待用户确认]` 标出来，列成"未决问题"候选，不要自己编造答案写成既定验收标准。

### 4. 汇总展示，等用户确认

把所有需求的缺口汇总成一份清单发给用户，然后明确问：
"以上缺口要不要都补进 PRD？可以整体确认，也可以说明只要哪几条。"

**不要在用户确认前直接编辑 `docs/PRD.md`。** 这份文档会被 `architect` 拆
Issue、被 `developer`/`reviewer` 当验收依据，静默改动会打乱下游流程。

### 5. 用户确认后再落盘

按用户圈定的范围，用 `Edit` 精确修改 `docs/PRD.md`：
- 追加验收标准：定位到对应需求的 `- **验收标准**：` 列表末尾插入新的 `- [ ]` 行。
- 新增子需求：仿照现有需求的格式（描述 + 验收标准），插入到合理位置，编号不与已有需求冲突。
- 有 `[待用户确认]` 且用户没有当场拍板的，写入 PRD 第 5 节"未决问题"，不要写成确定的验收标准。

改完后用一句话总结改了哪几处，不需要整段复述 PRD 内容。

---

## 边界

- 不采集全新需求（那是 `requirement-analyst` 的职责）——只对已有需求做"工程完整性"补强。
- 不做技术方案设计、不拆 Issue（那是 `architect` 的职责）。
- 不写代码。
- 发现的缺口如果涉及产品判断而非工程闭环（例如"要不要支持批量导出"这种全新功能),
  提出来但标注为建议性需求，别混进"缺口"里当成既有需求的漏洞。
