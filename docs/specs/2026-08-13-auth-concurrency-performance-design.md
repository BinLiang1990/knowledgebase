# 设计：接口鉴权 / 并发写冲突控制 / 查询性能优化（issue #15 选型）

对应 issue：[#15](https://github.com/BinLiang1990/knowledgebase/issues/15)（跟踪型，PRD §4.10/§4.6.2）。
本文给出三个事项各自的现状、方案对比与**推荐选型**，供确认后拆分实现 issue。三者相互独立，可分别排期。

---

## A. 接口鉴权

### A.1 现状与约束

- **全部接口无鉴权**，这是写进对接约定的阶段性决定（《对接接口文档-约定基准版》§1）；上线前置条件是"内网/专线或网关 IP 白名单"（遗留事项 #1）。
- 实际部署：正式环境挂**公网域名** `platform-enterprise.yicall.com`，nginx 反代 `/kb-api/` → 后端 7071 端口——不是纯内网，网络边界比约定假设更薄。
- 对接面已收窄为**只读 GET**（§0），写接口仅运营前端使用；对接文档明确：企业库的 HMAC 方案不可复用，未来鉴权方案须保留**兼容过渡期**，不一刀切。
- 关联事项：#31（操作人/来源身份识别）需要知道"哪个系统在调用"——鉴权方案应顺带解决调用方识别。

### A.2 方案对比

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| A1 网关 IP 白名单 | nginx `allow/deny` 或云安全组限制 `/kb-api` 来源 | 零代码、立即可做，是约定里的上线前置 | 粒度粗：区分不了调用方；对接方出口 IP 变更要改运维配置；对公网域名只是缩小暴露面 |
| **A2 静态 API Key（推荐）** | 请求头 `X-API-Key`；key 落库（调用方名称 + key 哈希 + scope + 状态），FastAPI 依赖统一校验；`AUTH_ENABLED` 开关默认关 → 发 key、双方联调、协调日期后再开强制（满足"兼容过渡期"承诺） | 实现小（~1 天）；**每个调用方一把 key** → 天然获得调用方身份，为 #31 铺路；scope 区分 read（对接方，只放行 GET）/ write（运营前端） | 明文传输依赖 HTTPS/内网；不防重放（内网场景可接受） |
| A3 HMAC 签名 | 时间戳+签名头，防重放 | 安全性最高 | 实现与联调成本数倍于 A2；对接文档已判定企业库 HMAC 不可复用=等同新做；内网/白名单叠加下收益边际小 |
| A4 OAuth2/JWT | 标准令牌体系 | 生态标准 | 需要 IdP/用户体系，v1 没有；overkill |

### A.3 推荐：A1 + A2 组合

网络层保住白名单底线（运维项，不进代码），应用层上 API Key：

1. 新表 `api_client`：`id / name / key_hash(SHA-256) / scope(read|write) / status / created_at`；key 只在创建时展示一次。
2. FastAPI 全局依赖：`AUTH_ENABLED=false`（默认，现状不变）时直通；开启后校验 `X-API-Key`，scope=read 仅放行 GET，`/health` 豁免。
3. **运营前端不改代码**：nginx 在前端同域的 `/kb-api/` location 里 `proxy_set_header X-API-Key <写 key>` 注入（key 不进浏览器）。代价是"经前端域名的请求全放行"，运营侧的人员级控制仍属 #31/登录体系范畴。
4. 对接方切换：发 read key → 文档更新（§7 通知承诺）→ 约定日期开启 `AUTH_ENABLED`。

**工作量**：后端 ~1 天（表+迁移+依赖+配置+测试）+ 运维半天（nginx/白名单）+ 对接方协调。

## B. 并发写冲突控制

### B.1 现状与真实风险

现有点状防御：revoke 的幂等 UPDATE（WHERE revoked=False）、标题/名称唯一约束、enabled-dimensions 竞态的文档化处理。仍存在的窗口（都源于"读链状态 → 写"的非原子性）：

| 场景 | 后果 |
|---|---|
| **写新版本 vs 整链撤回并发**：create/edit 检查链非撤回后 INSERT，期间 revoke 的批量 UPDATE 已执行 | 新行 `revoked=False` 落在已撤回链上 → 破坏"整链同撤回态"不变式（`compute_all_answer_groups` 的前提），组展示错乱 |
| 两个 edit 同时迁移同一条链 | 双份"迁移后新链"，数据不坏但语义重复 |
| reactivate 判定（issue #32 新增的"链是否撤回态→是否必填原因"）与并发撤回 | 原因校验被绕过或误判 |

写入方全部是运营侧（单前端 + 少量人），并发概率低——但一旦发生是**不变式级**破坏，修数据成本高。

### B.2 方案对比

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| B1 行锁 `SELECT ... FOR UPDATE` | 写端点先锁链上现有行 | 标准做法 | **锁不住"还不存在的链"**（首写场景无行可锁），gap lock 行为随隔离级别变化，心智负担大 |
| **B2 MySQL 命名锁 `GET_LOCK`（推荐）** | 写端点入口按 `kp:{kp_id}:chain:{coord_hash}` 获取命名锁（timeout 3s），临界区覆盖"读态→校验→写"，请求结束释放 | 与行存在性无关（天然覆盖新链/首写）；语义直白；实现是一个 context manager 进 4 个写端点（create/edit/promote/revoke）；低写入量下开销可忽略 | 锁在 MySQL 连接上，需保证同连接释放（依赖现有"每请求一 Session"即可）；跨库多实例仍有效（锁在 MySQL 服务端） |
| B3 乐观锁（版本号） | 链上加 version 字段比对重试 | 无锁等待 | 链是"追加行"模型，没有承载 version 的单行，需新表或改语义；客户端要处理重试——成本明显高于收益 |

### B.3 推荐：B2

- 粒度：知识点 + 条件链（`edit` 迁移场景需按序锁旧链+新链，按 key 排序加锁避免死锁）。
- 超时 3s → `BusinessError("该答案正被其他操作修改，请稍后重试")`。
- **工作量**：~0.5 天。集成测试受测试库隔离问题限制（conftest 会重置真实库），先以纯逻辑+人工并发验证，DB 集成测试挂在测试隔离解决之后。

## C. 大规模查询性能

### C.1 现状热点（按对接方调用路径实测代码）

| 路径 | 现状 | 量级影响 |
|---|---|---|
| **`GET /knowledge-points`（列表+条件筛选，对接方主查询）** | 每个 KP 调一次 `compute_live_groups`（1 次 SELECT）+ 其内部 `_dimension_weights`（再 1 次）→ **每请求 2N+2 次查询** | 几千 KP = 单请求数千次 RDS 往返，是最先撞墙的点 |
| 全局操作日志 | 全表 answers 载入内存推导 | 内部页面用，数据增长后再处理 |
| `resolve` 单点 / stats / 详情页各接口 | 常数次查询 | 无压力 |

### C.2 方案对比

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **C1 列表接口批量化（推荐，先做）** | 一次查询取整库有效 answers（+一次维度权重），内存按 KP×coord_hash 分组选 live 版本，复用现有 `resolve()` 纯函数——answer-relations 的 `collect_endpoints` 已验证同一模式 | 数千次查询 → **2 次**；纯重构零新组件；行为可与旧实现逐字段对齐 | 整库 answers 进内存（万级行 × 小字段，几十 MB 内，可接受） |
| C2 列表分页/筛选下推 | list 接口加可选 `limit/offset`（缺省保持全量，向后兼容对接约定） | 给万级以上留通道 | 对接方要适配（可选参数，不强制） |
| C3 缓存（Redis/进程内 TTL） | 读多写少适合 | 快 | 新组件 + 失效正确性成本；几千量级下 C1 已够，**过早** |
| C4 预计算/物化 live 表 | 写时维护当前版本表 | 查询最快 | 写路径复杂化、与撤回/恢复/迁移语义纠缠；**过早** |

### C.3 推荐：C1 立即做 + C2 顺带做；C3/C4 挂起，触发条件=单库答案行数过 5 万或列表 P95 > 1s（先加简单耗时日志观测）

**工作量**：C1+C2 约 1~1.5 天（含与旧实现的对拍验证）。
