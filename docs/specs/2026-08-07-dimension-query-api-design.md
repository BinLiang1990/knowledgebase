# 维度只读查询 API 设计文档（issue #3）

## 1. 范围

实现 `docs/PRD.md` §4.2、§4.3 的**只读查询**部分：

- 全局维度定义查询：只返回 `status=active` 的维度
- 知识库启用维度查询：返回某知识库当前启用的维度**完整定义**（不是只给 key 数组）

不含（见 issue #3 Out of Scope，留给 issue #9）：维度定义的新增/修改/停用；知识库启用维度的勾选/取消勾选写接口；§4.2 P0 行提到的"内部管理列表"（含已停用、含"全局共有多少条答案在用"统计）——那是维度管理页自己的视图，本 issue 只做**对外查询接口**这一半。

## 2. 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/dimensions` | 全局维度定义列表，只含 active |
| GET | `/knowledge-bases/{kb_id}/enabled-dimensions` | 该知识库启用的维度完整定义列表 |

两个接口返回的对象形状一致，直接采用 issue #3 Proposed Change 里给出的示例形状：

```
{ key, label, field_type, weight }
```

不含 `default_value`/`status`/`created_at` 等字段——issue 原文给的示例就是这四个字段，`status` 对这两个接口而言永远是常量（都已经被过滤成 active），没有必要占位暴露。

`/knowledge-bases/{kb_id}/enabled-dimensions` 挂在现有 `knowledge_base` 路由（issue #2）下，复用其 `_get_or_404` 找不到知识库时返回 404 的既有逻辑；`/dimensions` 是新的、独立的 `dimension` 路由（无知识库作用域）。

## 3. 需要明确的工程细节

1. **"知识库详情接口内嵌 enabled_dimensions" 是建议,不是验收标准。** issue 原文用"建议"措辞,且验收标准写的是"知识库详情**/**启用维度接口"(二选一,只要有一个能满足即可)。issue #2 目前没有单独的知识库详情(单条 GET)接口,只有列表。为了不在没有明确验收要求的情况下改动 issue #2 已经合并评审过的 `KnowledgeBaseOut` 契约,本 issue **只做独立的 `enabled-dimensions` 接口**,不去新增"知识库详情"接口或往列表接口里塞 `enabled_dimensions` 字段。如果后续第三方真的需要"一次查询拿到知识库+启用维度"的合并视图,作为独立的后续需求单独评估,不在这里顺带做。（对抗式自校指出：issue 给"建议内嵌"的理由——"避免第三方要查两次接口再自己拼装"——是一个真实的易用性诉求，这里只是暂不动手，不代表这个诉求不重要，值得在验收时跟 issue 提出者确认一下。）

2. **全局维度停用要联动过滤知识库的启用维度列表,而不是只看 join 表。** §4.3 原文："维度定义本身的停用/启用是全局操作,会同时影响所有已启用该维度的知识库"。`knowledge_base_enabled_dimension` 这张 join 表本身不会因为维度被全局停用而自动删行——**查询时必须再 `JOIN dimension_definition` 并过滤 `status='active'`**,不能只看 join 表"存在这一行"就认为已启用。**实现时必须用 INNER JOIN(SQLAlchemy 的 `.join()`),不能用 `.outerjoin()`**——outer join 会让已停用维度的行以 NULL 填充的方式继续出现在结果集里而不是被排除。这是本 issue 唯一一条容易被漏掉的业务规则,单独写测试覆盖(全局停用一个已被 KB 启用的维度,验证该维度从这个 KB 的启用列表里消失)。

3. **`enabled-dimensions` 是否要求知识库本身是 active 状态——这是一个未被 PRD/issue 明确settle的假设,不是已确认的结论。** §4.1 停用的效果原文是"知识库列表不再展示、无法进入其知识点列表",字面只提到列表和知识点,没提启用维度查询；但也可以读成"无法进入"泛指整个知识库(包括它的子资源)。PRD 和 issue 都没有明确到能排除任一种读法。**本设计选择更宽松的默认值：对已停用的知识库同样正常返回其启用维度列表**,理由是只读查询、不影响任何写路径、不泄露敏感信息,这是风险更低的默认行为，比"直接挡掉"更容易在后续澄清后收紧,不容易在澄清后需要放宽。用一个测试把这个选择显式锁定下来,方便以后 PRD 澄清后对照修改，而不是被静默覆盖。只有 `kb_id` 完全不存在时才 404。

4. **列表排序。** 两个接口都按 `key` 升序返回,纯粹为了结果确定性,不是业务要求。

5. **返回字段形状的依据。** `{key,label,field_type,weight}` 四个字段是 issue #3 Proposed Change 里给出的具体例子，不是 PRD §4.2/§4.3 原文的表述（PRD 里没有"完整定义"这个精确措辞，那是 issue 验收标准里的说法）。issue 自己给的示例形状比验收标准的模糊表述更具体、更权威，本设计按示例形状实现。

## 4. 测试计划

- `/dimensions`：只返回 active,排除 deprecated；返回字段恰好是 `{key,label,field_type,weight}` 四个
- `/knowledge-bases/{id}/enabled-dimensions`：
  - 返回该知识库启用的维度完整定义
  - 全局停用一个已启用的维度后,该维度从结果中消失（核心业务规则）
  - 未启用任何维度时返回空列表,不报错
  - `kb_id` 不存在 → 404
