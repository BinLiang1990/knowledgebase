## 0. 关键决策记录

| # | 问题 | 结论 |
|---|---|---|
| 1 | 关联的范围 | **任意两条答案之间**，不限知识点、不限知识库。重点场景：一个知识点里某个维度条件下的答案，和**其他知识库**的知识点的某条答案产生关联。同知识库、同知识点内不同条件的答案对也允许（是上述定义的自然子集） |
| 2 | 关联的单位 | **版本链级**：关联挂在"知识点 + 条件组合(coord)"上，展示与生成始终取该链的**当前生效版本**内容；版本链出新版本后关联不失效，但被标记"内容已更新"（stale），提示重新分析 |
| 3 | 触发方式 | **手动为主**：(a) 用户在某条答案上点「分析关联」按钮 → 系统全库召回相似答案并生成关联；(b) 用户**手动添加**指定的两条答案的关联。**不做**数据写入时自动触发（预留扩展点，后续如需可复用同一套任务设施，见 §9 Non-goals） |
| 4 | 相似答案怎么找（召回） | **向量召回**：答案内容经机房 Ollama 向量模型（走 FastGPT/网关的 OpenAI 兼容 embeddings 接口）转成向量，存 MySQL；分析时余弦相似度取 Top-K（默认 10）。规模预期几千知识点/万级答案，Python 内存暴力计算足够，**不引入向量数据库** |
| 5 | 关联描述怎么产生 | 召回后的每一对，调用 LLM 生成一段中文描述（一次调用批量生成整批）；**手动添加**时描述可以人工填写，也可以点"AI 生成" |
| 6 | LLM 通道 | 走**可配置的 OpenAI 兼容网关**（机房 FastGPT/OneAPI），embeddings 与 chat 各自独立配置 base_url/key/model；不绑定特定云厂商（见 §10.2 待确认） |
| 7 | 同步还是异步 | 分析是**异步任务**：点击按钮 → 立即返回任务 ID → 页面轮询进度。理由：首次分析可能要补齐全库缺失向量（万级 embedding 调用）+ 1 次 LLM 调用，秒级到分钟级不等，不能挂在请求里 |
| 8 | 任务队列选型 | **MySQL 任务表 + 应用进程内后台 worker 线程**，不引入 Redis/Celery（单机 Docker 手动部署，运维成本优先；表结构可平移到独立 worker） |
| 9 | 分析结果要不要人工确认 | **不需要确认，直接保存**为 `source=ai` 的关联；用户可删除任何一条。（备选"建议→确认"流程被否：多一步操作、价值有限） |
| 10 | AI 关联与手动关联冲突 | 同一答案对只有一条关联记录。手动添加/手动改写过的（`source=manual`）**不会**被后续 AI 分析覆盖；`source=ai` 的会被新分析结果覆盖更新 |
| 11 | 网关不可用/未配置怎么办 | 功能可降级：未配置网关时「分析关联」按钮禁用并提示；手动添加（人工填描述）不依赖网关，始终可用 |

## 1. 背景与目标

知识分散在多个知识库中，彼此存在事实上的引用、重叠、上下游关系——例如"经验库"里某条处置方案，与"制度库"里某条规定的特定租户答案讲的是同一件事。目前系统对这种关系零感知，使用者只能靠记忆和搜索自行拼接。

**本次目标**：

1. 用户对任意一条答案发起"分析"，系统自动在**全部知识库**范围内找出内容相关的答案，并为每一对生成一段说明相互关系的中文描述；
2. 用户也可以手动指定两条答案建立关联，描述可人工填写或 AI 生成；
3. 关联在两端知识点的详情页均可见、可删除；答案内容更新后关联提示"内容已更新"，可一键重新分析。

---

## 2. 术语定义

| 术语 | 说明 |
|---|---|
| 关联(Answer Relation) | 两条答案（版本链）之间的一条无向关系记录：两端定位（知识库/知识点/coord）+ 一段关系描述 + 来源（AI 分析 / 手动） |
| 关联端点(Endpoint) | `(knowledge_point_id, coord_hash)` 唯一确定的一条版本链；展示与生成取其当前生效版本（`compute_live_groups` 口径） |
| 分析(Analyze) | 以某个端点为中心的一次异步任务：召回全库相似端点 Top-K → LLM 批量生成描述 → 落库为 `source=ai` 的关联 |
| 向量(Embedding) | 端点当前生效内容经向量模型得到的浮点数组，随内容哈希缓存于 MySQL，内容不变不重算 |
| 召回(Recall) | 用中心端点向量对全库端点向量做余弦相似度排序，取 Top-K 且相似度 ≥ 阈值的端点作为候选 |
| stale（内容已更新） | 关联记录上保存的两端内容哈希，任一端与该链当前生效版本不一致；旧描述仍展示，提示可重新分析 |

## 3. 功能需求

### 3.1 发起分析 🔴 P0

- 入口：知识点详情页「当前答案」tab，每张答案卡片提供「分析关联」操作（见 §5）。
- `POST /knowledge-bases/{kb_id}/knowledge-points/{kp_id}/answer-relations/analyze`，body：`{"coord_hash": "..."}`（该知识点下某条有效链）。
- 行为：登记一条分析任务（同端点已有进行中任务则复用，不重复登记），立即返回 `{"task_id": ..., "status": "pending"}`。
- 前置校验：目标链存在且未撤回、有生效版本；网关未配置时返回业务错误「关联分析未启用」。

### 3.2 分析任务执行（worker） 🔴 P0

```
pending → generating → done
                       ├→ failed（retry_count ≥ 3，或网关不可用）
                       └→ pending（可重试错误，退避后重试）
```

单个任务步骤：

1. **向量补齐**：扫描全库全部有效端点（所有知识库、所有知识点的未撤回链的当前生效版本），对"无向量或内容哈希已变化"的端点分批调用 embeddings 接口补齐（批大小可配，默认 32 条/批）。增量场景下通常只有零星几条要补。
2. **召回**：中心端点向量 × 全库向量余弦相似度，取 Top-K（默认 10、阈值默认 0.60，可配），排除：中心端点自身、已存在 `source=manual` 关联的对。
3. **生成描述**：候选对分批（≤10 对/次）调用 chat 接口，输入包含每端的「知识库名 / 知识点标题 / 维度条件（用维度显示名渲染）/ 内容（超长截断，默认 4000 字）」，要求输出结构化 JSON（每对一段 100~300 字中文描述，说明关系类型：一致/互补/引用/上下游/冲突等，冲突必须点明）。
4. **落库**：逐对 upsert 关联记录（`source=ai`，覆盖旧 ai 记录，跳过 manual）；本次分析未再命中的旧 `source=ai` 关联**保留不删**（关联是累积资产，删除权在用户）。
5. 任务记录进度字段（`phase`: embedding/recall/generate，`progress`: 已处理/总数），供前端轮询展示。

### 3.3 手动添加关联 🔴 P0

- `POST /answer-relations`（全局路由，不挂在单个知识库下），body：两端 `{kb_id, kp_id, coord_hash}` + `description`（可空）+ `generate: bool`。
- `generate=true` 且 description 为空 → 登记一个"单对生成"任务（复用 worker 的生成步骤）；否则直接以人工描述落库，`source=manual`。
- 前端提供级联选择器：知识库 → 知识点（可搜标题）→ 条件组合（列出该知识点全部有效链）。
- 同一对已存在关联 → 返回业务错误提示已存在（可在详情里编辑）。

### 3.4 查询、编辑与删除 🔴 P0

- `GET /knowledge-bases/{kb_id}/knowledge-points/{kp_id}/answer-relations`：该知识点全部关联（其任一端属于该知识点即返回），含对端的 kb 名称/知识点标题/coord/当前内容摘要（前 200 字）、描述、source、stale 标记、生成时间。
- `GET .../answer-relations?coord_hash=...`：过滤某条链的关联（供答案卡片角标跳转）。
- `PATCH /answer-relations/{id}`：人工改写描述（改写后 `source` 变为 `manual`，此后 AI 分析不再覆盖）。
- `DELETE /answer-relations/{id}`：物理删除（关联非留痕数据，v1 不做软删）。
- `GET /answer-relations/tasks/{task_id}`：任务进度轮询。

### 3.5 stale 与重新分析 🟡 P1

- 查询时动态比对关联记录上的内容哈希与两端当前生效版本 → `stale=true` 显示「内容已更新」角标。
- 卡片上提供「重新生成描述」：对该对登记单对生成任务（manual 的关联也允许手动触发重新生成，生成后仍为 manual？——否，重新生成即接受 AI 内容，source 转回 ai）。

### 3.6 撤回/删除的联动 🔴 P0

| 事件 | 行为 |
|---|---|
| 某条链被整链撤回 | 涉及它的关联保留，展示时标记「对端已撤回」（灰态）；撤回链恢复后自动恢复正常展示 |
| 知识点软删除 | 同上，标记「对端知识点已删除」 |
| 知识库停用 | 同上处理；对端信息仍可见（与"历史永久可查"的产品口径一致） |

## 4. 召回与生成的技术约束

1. **embeddings 接口**：OpenAI 兼容 `POST {EMBEDDING_BASE_URL}/v1/embeddings`，`{"model": EMBEDDING_MODEL, "input": [ ...batch ]}`。经 FastGPT/OneAPI 网关转发到机房 Ollama 向量模型。**前置验证见 §10.1**。
2. **chat 接口**：OpenAI 兼容 `POST {LLM_BASE_URL}/v1/chat/completions`，JSON 输出用 prompt 约束 + 解析失败重试一次（网关/本地模型对 response_format 支持不一，不强依赖）。
3. **向量存储**：`answer_embedding` 表，vector 存 JSON 数组（万级 × 1024 维 float，全量载入内存 < 100MB）；召回用 numpy 暴力余弦，几千~几万条毫秒级。**不引入向量数据库/不依赖 MySQL 向量类型**（当前 MySQL 8.0 不支持）。
4. **成本账**：一次分析 = 增量 embedding（通常 0~几批）+ 1~2 次 chat 调用（K=10）。首次冷启动全库补向量约 万级条÷32/批 ≈ 数百次 embedding 调用，一次性成本，worker 内串行执行并可通过任务进度观察。

## 5. 页面展示

### 5.1 入口

**「当前答案」tab 的每张答案卡片**：

```
┌─ 条件: 租户=示例租户B ────────────── 关联 3 │ [分析关联] ─┐
│ （答案内容……）                                            │
└──────────────────────────────────────────────────────────┘
```

- `关联 3` 角标：该链已有关联数，点击 → 跳「答案关联」tab 并定位到该链分组；无关联时不显示。
- `分析关联`：发起 §3.1 的任务；进行中变为进度态（“分析中 · 召回 8/10”），完成后 toast + 角标刷新。

### 5.2 「答案关联」tab（知识点详情页第 5 个 tab）

```
│  │   两条答案针对同一退货流程：本答案是租户B的执行细则，       │ │

│  └─────────────────────────────────────────────────────────┘ │
│  ┌─────────────────────────────────────────────────────────┐ │

├──────────────────────────────────────────────────────────────┤
```

展示规则：

| 要素 | 规则 |
|---|---|
| 分组 | 按"本知识点侧的链"分组（默认答案组置顶，其余按 coord_hash 序） |

### 5.3 手动添加弹窗

级联选择对端：知识库下拉 → 知识点搜索选择 → 条件组合单选（列出有效链，显示条件徽章 + 内容前 100 字）→ 描述文本框 +「AI 生成描述」按钮（异步，生成后填入文本框可再编辑）→ 保存。

### 5.4 轮询

分析任务进行中：`GET /answer-relations/tasks/{id}` 每 3s 轮询，展示 phase/progress；完成后失效 relations 查询缓存。tab 数据懒加载（与 timeline/logs tab 模式一致）。

## 6. 数据模型

**`answer_relation`**（无向，端点排序规范化：(kp_id, coord_hash) 较小者为 a）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT UNSIGNED PK | |
| kb_a_id / kp_a_id / coord_hash_a | BIGINT / BIGINT / CHAR(64) | 端点 A |
| kb_b_id / kp_b_id / coord_hash_b | 同上 | 端点 B；`UNIQUE(kp_a_id, coord_hash_a, kp_b_id, coord_hash_b)` |
| coord_a / coord_b | JSON | 快照（渲染用） |
| answer_a_id / answer_b_id | BIGINT UNSIGNED | 生成/添加时两端采用的版本 |
| content_hash_a / content_hash_b | CHAR(64) | 生成时内容哈希（stale 判定） |
| description | LONGTEXT | 关系描述 |
| source | ENUM(ai, manual) | 覆盖规则见 §0.10 |
| similarity | FLOAT NULL | AI 召回时的余弦相似度（手动为 NULL） |
| model | VARCHAR(100) NULL | 生成所用模型 |
| operator | VARCHAR(100) | 发起人（v1 固定 admin） |
| created_at / updated_at | DATETIME(6) | |

**`answer_embedding`**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT UNSIGNED PK | |
| knowledge_base_id / knowledge_point_id / coord_hash | — | `UNIQUE(knowledge_point_id, coord_hash)` |
| content_hash | CHAR(64) | 与向量对应的内容哈希 |
| model | VARCHAR(100) | 向量模型标识（换模型需全量重算，靠此字段判断） |
| vector | JSON | float 数组 |
| updated_at | DATETIME(6) | |

**`relation_task`**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT UNSIGNED PK | |
| kind | ENUM(analyze, generate_pair) | 全量分析 / 单对生成 |
| center_kp_id / center_coord_hash | — | analyze 的中心端点 |
| pair_relation_id | BIGINT NULL | generate_pair 指向的关联 |
| status | ENUM(pending, generating, done, failed) | |
| phase / progress_done / progress_total | VARCHAR(20) / INT / INT | 进度展示 |
| retry_count / last_error | TINYINT / VARCHAR(500) | |
| created_at / updated_at | DATETIME(6) | worker 启动时把遗留 generating 重置为 pending |

## 7. 配置项（backend/.env）

| 变量 | 默认 | 说明 |
|---|---|---|
| `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` / `EMBEDDING_MODEL` | 空 | OpenAI 兼容 embeddings 网关；任一为空则分析功能降级 |
| `RELATION_LLM_BASE_URL` / `RELATION_LLM_API_KEY` / `RELATION_LLM_MODEL` | 空 | OpenAI 兼容 chat 网关（可与上面同网关不同模型） |
| `RELATION_TOP_K` | 10 | 召回数量 |
| `RELATION_MIN_SIMILARITY` | 0.60 | 召回阈值 |
| `RELATION_EMBED_BATCH` | 32 | embedding 批大小 |
| `RELATION_MAX_CONTENT_CHARS` | 4000 | 送入 prompt 的单条内容截断 |

## 8. 非功能需求

1. 分析全程异步，任何写接口/查询接口性能不受影响；
2. 任务持久化于 MySQL，进程重启不丢；幂等（重复执行同一任务结果一致）；
3. 向量按内容哈希缓存，内容不变永不重算；换向量模型时按 model 字段识别并全量重算（worker 顺带完成）;
4. 网关调用设置超时（embeddings 30s/批，chat 120s）与重试（3 次退避）；
5. ⚠️ 测试隔离前置：现有 pytest 直连真实库（已知问题），本功能测试必须 mock DB/网关，或先解决测试库隔离。

## 9. 不做的事（Non-goals）

- 数据写入时自动触发分析（预留：触发矩阵接到 `relation_task` 即可，v1 不做）；
- 建议→人工确认的两段式流程；关联的变更留痕；跨知识点关联的批量全库扫描（"一键分析全库"）；向第三方接口暴露关联数据；关系图可视化（P2 单独立项）。

## 10. 待确认项（开发前必须关闭）

### 10.1 网关 embeddings 接口可用性 🔴 前置验证

FastGPT 本身的 OpenAPI 是"应用对话"接口，**不一定**透出裸 embeddings。需要确认外网可访问的地址上存在 OpenAI 兼容向量接口（FastGPT 配套的 OneAPI/网关通常有）。验证命令：

```bash
curl -s {外网网关地址}/v1/embeddings \
  -H "Authorization: Bearer {key}" -H "Content-Type: application/json" \
  -d '{"model": "{向量模型名，如 bge-m3}", "input": ["测试文本"]}'
# 期望返回 {"data":[{"embedding":[...]}], ...}
```

若只有 FastGPT 应用对话通道 → 需运维在网关上挂载向量模型，或开放 Ollama 的接口代理。**此项不通，召回方案需要换（退回"LLM 扫标题"或本地内嵌向量模型）。**

### 10.2 描述生成用哪个 chat 模型

走同一网关的机房模型（哪个？需给出模型名与上下文长度），还是外部云模型？决定 `RELATION_LLM_*` 的取值与 prompt 长度预算。

### 10.3 「分析关联」按钮的权限/频率

v1 无权限体系，但要不要做简单防抖（同端点 N 分钟内只允许一次分析）？默认建议：同端点存在进行中任务时按钮置灰即可，不另做频率限制。
