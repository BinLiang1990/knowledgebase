## 0. 关键决策记录

产品模型经过多轮 demo 验证迭代，最终从"知识点单版本演进"改为"知识点 + 多条并存答案(Answer)"。以下是全部关键决策，后续章节均按最终结论编写：

| # | 问题 | 结论 |
|---|---|---|
| 1 | 持久化范围 | **要落地成正式系统**：需要后端服务 + 数据库，不再是纯前端演示 |
| 2 | 删除知识点的语义 | **软删除**：知识点整体停用，历史答案与留痕仍可查询；可在回收站恢复 |
| 3 | 编辑是否总是生成新版本 | **是**，需要留痕；不提供"编辑当前版本不留痕"的能力 |
| 4 | 维度字段类型范围 | **文本 / 数值 / 时间 / 布尔**；不做单选(枚举) |
| 5 | 角色权限 / 操作人记录 | **需要记录操作人**；操作人身份将来从外部系统集成传入，v1 阶段固定为 `admin`；不做角色权限区分 |
| 6 | 维度取值查询要不要支持区间 / 大于小于 | **不支持**。查询与答案的适用条件统一为"钉住某维度 = 某个值"的精确匹配，不做区间或比较运算符 |
| 7 | 查询条件之间要不要支持"或" | **不支持**，维度条件之间固定为"且" |
| 8 | 多租户要不要做成系统级隔离机制 | **不做**。"租户"就是维度定义里一个普通维度(`key=tenant`，文本类型)，和其他维度一样走通用的维度增删改查/答案条件流程；v1 默认只预置一个租户取值，不做数据库级隔离(分库分表、强制 `WHERE tenant_id`)，真正的多租户隔离留作后续单独立项 |
| 9 | 知识点的内容要不要允许"多个并存的说法" | **要**。同一个知识点在不同维度条件下可以有不同的、互不覆盖的说法(答案)，而不是只有一条随时间演进的主线内容(见 §2、§4.4) |
| 10 | 维度要不要有优先级 | **要**，即"权重"(1–100)。查询条件没有精确命中任何一条答案时，用"条件更具体 → 涉及维度权重更高 → 版本更新"的顺序回退匹配 |
| 11 | 维度是否所有知识库通用 | **定义全局共享，启用按知识库勾选**。维度定义(key/字段类型/权重)全局维护一份；每个知识库需要在"知识库设置"里勾选要启用哪些维度，才能在写答案时用它做条件 |
| 12 | 要不要保留独立的"按维度查询"页面 | **不需要**。条件筛选(钉维度=值、时间穿梭)直接合并进"知识点列表"页，不再单独做一个查询页面 |

## 0.1 交付优先级

**驱动因素**：知识库的"维度查询"、"知识库 CRUD"、"知识点 CRUD" 需要**立即**对接给第三方使用，其余能力可以在此之后陆续补齐。优先级标注贯穿全篇 §4 各小节标题及关键表格，图例如下：

| 优先级 | 含义 |
|---|---|
| 🔴 P0 | 立即实现——第三方对接的最小可用集合，本轮必须交付 |
| 🟡 P1 | 紧接着实现——完善答案生命周期与审计能力，不阻塞第三方对接 |
| 🟢 P2 | 可延后——锦上添花的可视化/分析能力 |

**P0 范围与依赖说明**（对应 §4 各小节）：

| 能力 | 对应章节 | 说明 |
|---|---|---|
| 知识库 CRUD | §4.1 | 完整增删改查 |
| 知识点 CRUD | §4.4 | 完整增删改查 |
| 答案写入/编辑（基础） | §4.5 部分 | 知识点本身不携带内容，"知识点 CRUD"要读写到实际内容，必然依赖"写一条答案 / 编辑答案"这两个操作一并交付；**"设为默认"、"撤回"可以先不做**，作为 P1 |
| 维度定义查询 | §4.2 部分 | 第三方做"维度查询"至少需要能读取维度定义列表(key/label/字段类型/权重)；**维度定义的新增/修改/停用**（即维度本身的管理）先由内部沿用 demo 里的管理界面/直接写库，接口层面可以作为 P1 |
| 知识库启用维度查询 | §4.3 部分 | 第三方查询时需要知道"这个知识库能用哪些维度"，读接口是 P0；勾选/取消勾选的写接口可以作为 P1 |
| 按维度条件查询知识点 | §4.6 + §4.6.1 | 这就是"维度的查询"能力本身：给时间 + 维度条件，解析返回命中的知识点/答案内容，精确匹配 + 权重回退逻辑必须在 P0 就实现，否则查询结果不可信 |

不在 P0 范围、但影响"知识点 CRUD"完整度的操作（编辑答案时的"设为默认""撤回"、知识点详情页的版本历史/变更留痕/立体全景、全局操作日志、统计卡）全部归为 P1/P2，见各小节标注。

## 1. 背景与目标

通过 `frontend-mock/` 静态 HTML 原型的多轮迭代（先验证"知识点 + 版本 + 维度过滤"的解析逻辑，再验证知识库容器、维度管理、多答案并存与权重回退匹配、变更留痕、全局操作日志等能力），最终稳定出一套"按知识库分组、维度可扩展、一个知识点下多条答案按条件互不覆盖并存"的知识库数据模型。

**本次目标**：把 demo 验证过的模型，落地成一个有后端 + 数据库支撑的正式功能模块：

1. 用户可以对"知识库"做完整的增删改查，知识点归属于具体知识库，数据持久化保存
2. 用户可以对"维度"本身做增删改查（全局定义 + 按知识库启用），每个维度有明确的字段类型和权重
3. 一个知识点下可以维护多条"答案"，按维度条件区分、互不覆盖，支持"设为默认""撤回"
4. 查询知识点时可以带上维度条件与时间点，复用 demo 已验证的"精确匹配 → 权重回退"解析逻辑
5. 每个知识点、以及跨知识库的全局视角，都能看到完整的变更留痕，支持从留痕直接撤回

## 2. 术语定义

| 术语 | 说明 |
|---|---|
| 知识库(Knowledge Base) | 知识点的容器，拥有名称/描述/启用状态；知识点归属于具体的知识库，不同知识库互不影响 |
| 维度定义(Dimension Definition) | 全局共享的可扩展属性元数据：`key`(不可改)、显示名、字段类型(创建后不可改)、权重(1–100)、状态(启用/停用) |
| 知识库启用维度(Enabled Dimensions) | 每个知识库从全局维度定义中勾选的子集；只有被本知识库启用的维度，才能在这个知识库的答案里用作条件 |
| 知识点(Knowledge Point) | 一条知识的"主体"，拥有标题、唯一 ID(在其所属知识库内)、创建人/时间、启用状态；本身不直接携带内容，内容由其下的答案承载 |
| 答案(Answer) | 知识点在某个"维度条件组合"下的一份说法：适用条件(coord，0~N 个 `维度=取值`)、内容、生效时间、操作人、来源、是否已撤回。同一知识点下，不同条件组合的答案彼此独立、并存，互不覆盖 |
| 条件组合(coord) | 一条答案所写明的维度取值集合，如 `{}`(不写条件 = 默认)、`{租户: 示例租户B}`；条件组合相同的答案构成一条"版本链" |
| 版本链 | 同一知识点下、同一条件组合的答案按生效时间排列形成的链；再次编辑 = 在链尾追加新版本，历史版本永久保留、只读 |
| 默认答案 | 条件组合为空(`{}`)的那条答案；查询时若未指定任何维度条件，优先返回默认答案 |
| 设为默认 | 把某条答案的内容，作为默认答案版本链的新版本写入；不影响原答案本身 |
| 撤回 | 对某个条件组合的整条版本链做逻辑删除(而非物理删除)，需填写撤回原因；撤回后该条件下不再返回结果，但历史与留痕永久可查 |
| 精确命中(exact) | 查询给出的维度条件与某条答案的条件组合完全一致 |
| 权重回退(weighted) | 查询条件没有被任一答案精确命中时，在"条件兼容"(答案写明的条件都与查询相符，答案未写明的不参与比较)的答案里，按"条件更具体 → 权重总和更高 → 版本更新"的顺序选出最匹配的一条 |
| 变更留痕 | 由答案的创建/编辑/撤回历史自动推导出的操作流水：时间、操作人、动作(写答案/改答案/撤回答案)、条件、变更前后内容、来源、状态 |
| 操作人(Operator) | 产生某次变更的人；v1 阶段固定为 `admin`，后续从外部身份系统集成 |
| 来源(Source) | 答案内容的产生方式；v1 阶段固定为"人工填报"(新增/编辑答案)或"人工编辑"(撤回)，为后续对接外部数据源(如第三方数据/AI 生成)预留字段 |

## 3. 用户与角色

v1 **不做角色权限区分**——所有可访问该功能的用户拥有同等的增删改查能力。每次写操作（知识库/维度/知识点/答案的增删改）都会记录操作人，v1 阶段固定写入 `admin`，字段结构上保留未来对接外部身份系统的空间（见 §7 集成点）。

## 4. 功能需求

### 4.1 知识库管理（增删改查）🔴 P0

| 操作 | 说明 |
|---|---|
| 新增 | 填写名称(必填)、描述(可选)、启用维度(可选，2026-08-12 增补：创建弹窗内直接勾选，与建库同一事务生效，免去建库后必须再进"知识库设置"的二段式操作；不勾 = 不启用任何维度，之后仍可到"知识库设置"调整)。**名称需全局唯一**(见下方校验规则) |
| 查看 | 知识库列表，展示每个知识库当前生效的知识点数量、启用状态、创建时间 |
| 修改 | 可改名称、描述；改名后同样要满足唯一性校验 |
| 停用 | 逻辑停用：知识库列表不再展示、无法进入其知识点列表；知识点与答案数据不受影响，重新启用后可继续访问 |

**校验规则**：
- [ ] 当新增或修改知识库名称与**现有任意知识库**（含已停用的）完全重复时，接口应拒绝并返回明确错误（如 `knowledge_base_name_duplicated`），不允许重名。

### 4.2 维度定义管理（全局，增删改查）🔴 P0（查询）/ 🟡 P1（增删改）

每个维度定义包含：

| 字段 | 说明 |
|---|---|
| `key` | 唯一标识，创建后不可修改 |
| `label` | 显示名称，可修改 |
| `field_type` | 字段类型，**创建后不可修改**；需要变更类型时应停用旧维度、新建一个新维度 |
| `weight` | 权重(1–100)，用于查询未精确命中时的回退排序，可修改 |
| `default_value` | 默认取值提示(可选)：仅用于"写答案"表单里该维度输入框的预填建议，不做强制校验 |
| `status` | 启用 / 停用 |

**字段类型集合（v1 范围，已确认）**：

| 类型 | 说明 |
|---|---|
| 文本(Text) | 任意字符串 |
| 数值(Number) | 整数或小数 |
| 时间(Date) | 日期（是维度自己的取值，不是"生效时间"） |
| 布尔(Boolean) | 是/否 |

> 不做单选(枚举)。所有类型在"答案条件"与"查询条件"里都统一做**精确相等匹配**，不支持大于/小于/早于/晚于/包含等比较运算符，也不支持区间查询（详见 §0 决策 #6）。

**维度定义的增删改查**：

| 操作 | 优先级 | 说明 |
|---|---|---|
| 查看 | 🔴 P0 | 维度定义列表，含"全局共有多少条答案在用"的统计；第三方"维度查询"依赖这个接口知道有哪些维度可用。**内部管理列表**（维度管理页）展示全部维度（含已停用），供管理员重新启用；**对外的维度查询接口**只返回 `status=active` 的维度，已停用的维度不返回 |
| 新增 | 🟡 P1 | 填写 label(同时作为 key)/field_type/weight/默认取值提示 |
| 修改 | 🟡 P1 | 可改 label、weight、默认取值提示；`field_type` 不可改 |
| 停用 | 🟡 P1 | 逻辑停用：不影响历史答案里已经写入的取值；新增/编辑答案时该维度不再出现在可选列表里 |

### 4.3 知识库内 · 启用维度 🔴 P0（查询）/ 🟡 P1（勾选/取消勾选）

每个知识库需要单独维护一份"启用维度"清单（从全局维度定义中勾选）：

- 只有本知识库启用的维度，才会出现在本知识库"写答案"的条件选择器、以及"知识点列表"的条件筛选器里
- 取消勾选（停用）不影响本知识库历史答案里已经写入的该维度取值，只影响之后能否继续选用
- 维度定义本身的停用/启用是全局操作，会同时影响所有已启用该维度的知识库

> P0 阶段至少要能**读取**"某知识库启用了哪些维度"（供查询接口内部校验条件合法性、供第三方了解可查询范围）；勾选/取消勾选的写接口作为 P1，先由内部管理界面维护即可。

### 4.4 知识点管理（增删改查）🔴 P0

| 操作 | 优先级 | 说明 |
|---|---|---|
| 新增 | 🔴 P0 | 填写标题(必填，**同一知识库内需唯一**，见下方校验规则)；可选填写一段"默认答案内容" + 生效时间，若填写则同时创建该知识点的默认答案(v1)；操作人写入 `admin` |
| 查看-列表 | 🔴 P0 | 展示知识库当前生效（未删除）的知识点，支持按标题关键字 + 维度条件筛选（见 §4.6），点击行可展开查看该知识点全部答案的分组树 |
| 查看-详情 | 🔴 P0（当前答案）/ 🟡 P1（版本历史、变更留痕）/ 🟢 P2（立体全景） | 展示知识点的完整信息：当前答案(带条件筛选)、立体全景（多维度可视化）、版本历史（按条件组合选择版本链）、变更留痕，四个分区（详见 §4.7），各分区优先级不同 |
| 修改标题 | 🔴 P0 | 直接修改知识点标题，不生成版本（标题不是答案内容，不需要留痕演进）；改名后同样要满足同知识库内唯一性校验 |
| 删除 | 🔴 P0 | **软删除**：知识点整体标记为已删除，需填写删除原因。删除后不出现在知识点列表与查询结果中；其下全部历史答案与留痕永久保留，可在回收站恢复 |
| 恢复 | 🔴 P0 | 从回收站恢复为正常状态，全部历史答案与版本照常可用 |

> "知识点 CRUD"里的"内容"实际存放在 §4.5 的答案上，因此本节的"新增/查看/删除/恢复"在 P0 阶段必须与 §4.5 的"写一条答案 / 编辑答案"一并交付，否则知识点只有标题、没有可查询的内容。

**校验规则**：
- [ ] 当新增或修改知识点标题与**同一知识库内**现有知识点（含已删除的）完全重复时，接口应拒绝并返回明确错误（如 `knowledge_point_title_duplicated`），不允许重名；跨知识库允许重复标题。

**v1 明确不支持（已确认，见 §8）**：
- 不支持第三方在创建知识点/答案时自带外部唯一键做 create-or-update（幂等 upsert）；知识点 ID 由系统生成，第三方需要自己保存映射关系
- 不支持跨知识库的知识点批量检索/增量同步接口；所有知识点操作都限定在单个知识库范围内

### 4.4.1 批量导入知识点 🟡 P1

支持在单个知识库内一次性批量创建多条知识点（含各自的默认答案）。用于第三方迁移存量数据时减少逐条调用的成本。具体的失败处理策略（整体回滚 vs 部分成功+失败清单）留待 P1 排期时再细化，本轮 P0 不包含此接口。

### 4.5 答案管理（增删改查）🔴 P0（写入/编辑）/ 🟡 P1（设为默认、撤回）

| 操作 | 优先级 | 说明 |
|---|---|---|
| 写一条答案 | 🔴 P0 | 填写内容(必填)、生效时间(必填)、适用条件(0~N 个"维度=取值"，维度只能从本知识库已启用的维度中选)、变更说明(可选)。条件组合为空 = 默认答案 |
| 编辑答案 | 🔴 P0 | 若条件组合不变：在该版本链尾部追加新版本，历史版本永久只读保留。若条件组合改变：原条件组合整条版本链**整体撤回**（记录迁移原因），在新条件组合下新增一条版本链的首个版本 |
| 设为默认 | 🟡 P1 | 把当前这条答案的内容，写成"默认答案"版本链的新版本；原答案本身不受影响，仍然存在 |
| 撤回 | 🟡 P1 | 对某个条件组合的整条版本链做逻辑删除，必须填写撤回原因；撤回后该条件下的查询不再返回结果，历史版本与留痕永久保留 |
| 重新启用（撤回的恢复） | 🟡 P1 | （issue #32，2026-08-12 增补，推翻原 §8"不支持撤回的撤回"）不提供独立按钮/接口，走正常"新增答案"路径：写入目标条件组合当前是撤回态时，必须额外填写**重新启用原因**（≤500 字），同一事务内整链恢复（撤回记录保留为历史，不清空）并追加新版本；变更留痕展示"撤回 → 恢复"两个条目，被恢复的撤回条目状态标"已恢复" |

> P0 阶段没有"撤回"接口时，误写的答案暂时只能通过"编辑"覆盖式修正（生成新版本掩盖旧内容），无法整组下线；如果第三方对接前就需要"撤回"能力，请提前告知以调整优先级。

**校验规则**：
- [ ] 写答案时若 `coord` 中包含**本知识库未启用**的维度 key，接口应报错拒绝（如 `dimension_not_enabled`），不做静默忽略或自动过滤。
- [ ] 同一条件组合(coord)下允许写入多条 `effective_time` 完全相同的答案；此时以 `created_at` 更新的一条作为该组的"当前版本"（见 §4.6.1、§5 排序规则更新）。
- [ ] 答案内容(`content`)、变更说明(`note`)**暂不设长度上限**（v1 决定，后续如遇存储或性能问题再重新评估）。

### 4.6 知识点列表 · 带条件筛选（取代独立查询页）🔴 P0

**输入**：
- 关键字（按知识点标题过滤）
- 查询时间：默认为"当前"，可切换为"回看某天"任选历史日期
- 0~N 组维度条件：从本知识库已启用的维度里选一个 + 填写取值（下拉钉选，非区间/非运算符），条件之间固定为"且"

**行为**：
- 无维度条件：展示知识库内全部匹配关键字的知识点，每行预览其"默认答案"（若没有默认答案，则回退展示全部答案里最新的一条，并提示"无默认·取最新"）
- 有维度条件：只展示"存在与条件兼容的答案"的知识点（详见 §4.6.1 解析规则），预览该条件下命中的答案，并标注是"精确命中"还是"未精确命中·按权重回退"
- 点击知识点行可展开，查看该知识点全部答案按"默认/单维度分组/组合条件"分层的树状展示（只读，编辑操作在详情页进行）

### 4.6.1 解析规则（demo 已验证，原样复用）🔴 P0

这是"维度的查询"能力的核心，第三方对接的可用性直接取决于这条解析规则实现是否准确，**必须**与 §4.6 一起在 P0 阶段交付、并对照 demo(`frontend-mock/`)做逐条回归验证。

对每个知识点，在给定的"查询时间 T + 维度条件 Q"下：

1. 只考虑生效时间 ≤ T、且未被撤回的答案版本；每个条件组合取该组内符合条件的最新一条，作为该组在 T 时点的"当前版本"——排序按 `effective_time` 降序，若 `effective_time` 相同则按 `created_at` 降序（后创建的胜出）作为第二排序键（见 §4.5 校验规则）
2. **若 Q 为空**：
   - 若存在条件组合为空的默认答案组 → 返回默认答案
   - 否则 → 回退返回全部答案组里生效时间最新的一条，并标注"无默认·取最新"
3. **若 Q 非空**：
   - 筛选出"条件兼容"的答案组：该组自己写明的每一个维度取值都必须与 Q 里对应维度的取值一致；Q 里问到、但该组没写的维度不参与过滤；该组写了、但 Q 没问到的维度也不参与过滤
   - 在兼容的答案组里，先分两档：**该组涉及的维度是否都被 Q 问到过**（即该组不依赖任何 Q 未指定的维度）排在"依赖了 Q 未问到的维度"的组之前——一个额外要求"场景=科技场景"但用户根本没勾选"场景"的组合条件，不能因为"涉及维度更多"就压过一条完全对应用户所问维度的单维度答案；同档内再按"条件更具体(涉及维度数更多) → 涉及维度的权重总和更高 → 生效时间更新"的顺序排序，取第一条
   - 若该结果的条件组合与 Q 完全一致（维度个数与取值都对上）→ 标注"精确命中"；否则标注"按权重回退命中"
   - 若没有任何兼容的答案组 → 该知识点在此条件下"未命中"，从筛选结果中排除

> 不支持维度条件之间的"或"逻辑；不支持数值/时间维度的区间或大小比较（详见 §0 决策 #6、#7）。

### 4.6.2 单点解析接口（供第三方直接查询）🔴 P0

§4.6 描述的是"知识点列表 + 条件筛选"这种面向界面浏览的形态；第三方作为 API 消费者，更常见的用法是**已经知道要问哪个知识点**，只需要"给定知识库 + 知识点 + 维度条件 + 查询时间，直接返回命中的答案"，不需要先拉列表再自己筛选。因此 P0 需要额外提供一个单点解析接口：

- 输入：`knowledge_base_id`、`knowledge_point_id`、查询时间(默认当前)、0~N 组维度条件
- 输出：命中的答案内容 + 命中方式(`exact` / `weighted` / `default` / `fallback-latest` / `none`)，逻辑完全复用 §4.6.1 的解析规则
- 与 §4.6 的列表筛选接口共享同一套解析引擎实现，避免两处逻辑不一致

**性能与规模**：v1 暂不针对大量知识点/答案的场景做专门优化（如缓存、预计算），先按 demo 验证过的"实时解析"方案实现；后续如果实际接入的知识点规模明显变大，再评估是否需要缓存层，**优先级 🟢 P2**。

### 4.10 对外接口通用约定 🔴 P0（响应结构）/ 🟢 P2（鉴权、并发控制）

面向第三方的所有 P0 接口统一遵循以下约定：

**响应结构（已确认，🔴 P0）**：所有接口返回统一的信封结构：

```json
{
  "code": 200,
  "data": {},
  "msg": "操作成功"
}
```

- `code`：`200` 表示成功；出现业务异常/校验失败时统一返回 `444`，具体原因写在 `msg` 里（v1 先不做细分错误码，如后续第三方需要按错误类型做程序化处理，再补充分错误码方案）
- `data`：成功时的返回内容，可以是对象（如详情接口）也可以是集合（如列表接口），无返回内容时为 `{}` 或 `[]`
- `msg`：成功固定为"操作成功"或具体说明；失败时说明失败原因

**鉴权方式（🟢 P2，待补充）**：第三方接口的鉴权方案尚未确定，v1 阶段暂不设鉴权限制（接口先放开），后续接入鉴权（API Key / 内网白名单 / 其他）时再补充设计，不阻塞本轮 P0 交付。

**并发写冲突控制（🟢 P2，待补充）**：同一知识点、同一条件组合(coord)被并发编辑/撤回时的加锁或冲突处理策略，v1 暂不做特殊处理，后续视实际接入情况评估是否需要行级锁/乐观锁，不阻塞本轮 P0 交付。

## 5. 数据模型（草案）

```
KnowledgeBase(知识库)
  - id                主键
  - name               全局唯一(唯一索引，含已停用的知识库)
  - description
  - status            active | deprecated
  - enabled_dim_keys   本知识库启用的维度 key 列表
  - created_at

DimensionDefinition(维度定义，全局)
  - key                主键，不可改
  - label
  - field_type         text | number | date | boolean，创建后不可改
  - weight             1–100
  - default_value      默认取值提示(可选，仅前端预填用)
  - status             active | deprecated
  - created_at

KnowledgePoint(知识点)
  - id                 主键(在所属知识库内唯一即可；v1 不支持第三方自带外部 ID 做 upsert)
  - knowledge_base_id  FK -> KnowledgeBase
  - title              同 knowledge_base_id 下唯一(唯一索引 knowledge_base_id+title，含已删除的)
  - status             active | deleted     // 由"删除/恢复"操作驱动
  - operator
  - created_at
  - deleted_at
  - delete_reason

Answer(答案)
  - id                 主键
  - knowledge_base_id  FK -> KnowledgeBase（与知识点保持一致，便于跨知识库统计/审计）
  - knowledge_point_id FK -> KnowledgePoint
  - coord              { [dimension_key]: value }   // 该答案写明的适用条件；{} = 默认答案
  - content
  - effective_time     生效时间(答案自身的业务时间，不是 created_at)
  - operator           v1 固定 "admin"
  - source             v1 固定 "人工填报" / "人工编辑"
  - note               变更说明(可选)
  - revoked            是否已被撤回(逻辑删除标记；同一 coord 的整条版本链共享同一撤回状态)
  - revoked_at / revoked_by / revoke_reason
  - created_at
```

**查询索引建议**：`Answer` 至少需要 `(knowledge_point_id, coord_hash, effective_time, created_at)` 复合索引，支撑"按知识点 + 条件组合找生效时间 ≤ 查询时间、且 `effective_time` 相同时按 `created_at` 取最新的未撤回版本"这一核心解析路径；`coord` 若落地为 JSON 字段，建议额外落一个规范化的 `coord_hash`（如维度按 key 排序后拼接的字符串）用于分组与索引，避免每次查询都做 JSON 内容比较。

## 6. 核心业务规则

1. **答案按条件组合(coord)分组，组内版本链只增不改**：同一知识点下，条件组合不同的答案彼此独立、永久并存；同一条件组合下的编辑，是在该组版本链尾部追加新版本，历史版本永久只读。
2. **条件组合变更 = 迁移**：编辑答案时如果改变了其适用条件，原条件组合的整条版本链会被整体撤回（记录迁移原因），新条件组合下新建一条版本链。
3. **默认答案是条件组合为空的那一组**：不需要专门的"是否默认"标记字段；"设为默认"操作的本质是往这一组里追加一条新版本。
4. **撤回是"整组"逻辑删除，但不是终态**：撤回作用于某个条件组合的整条版本链，而不是单个版本；必须填写撤回原因，写入留痕；不提供物理删除。2026-08-10 起：往一条已撤回的链写入新版本（新建答案/编辑追加/迁移进来/设为默认）会把该链整体恢复为未撤回状态，不是被永久拒绝——保持"整条链共享同一撤回状态"这条不变量，不允许出现部分行撤回、部分行不撤回的中间状态。
5. **维度取值类型强校验**：写入 `coord` 或作为查询条件时，必须按该 key 当前的 `field_type` 校验（数值必须能解析成数字，时间必须是合法日期，布尔必须是 true/false）。
6. **维度全局定义、按知识库启用**：维度定义（key/字段类型/权重）全局唯一维护一份；每个知识库单独维护一份"启用维度"清单，只有启用的维度才能出现在该知识库的答案条件与查询条件里。
7. **维度停用不影响历史**：已经写入历史答案里的维度取值永久保留、可查；停用（全局停用或知识库内取消启用）只影响"以后能否继续选用"。
8. **知识点软删除是粗粒度操作，独立于答案撤回**：知识点删除/恢复整体控制该知识点是否出现在列表与查询里；答案撤回是知识点内部某个条件组合的细粒度逻辑删除，两者互不影响、可独立操作。
9. **查询解析规则**：给定时间 + 维度条件，按 §4.6.1 的顺序解析——先看是否有精确命中，没有则按"条件更具体 → 权重更高 → 版本更新"回退；条件之间固定为"且"，不支持"或"、不支持区间查询、不支持比较运算符（详见 §0 决策 #6、#7）。
10. **操作人 / 来源 v1 固定值**：操作人固定写入 `admin`，来源固定写入"人工填报"或"人工编辑"；字段结构已在数据模型中预留，待外部身份系统 / 数据来源集成后，替换为真实来源，历史数据不需要回填。
11. **"租户"不做特殊系统隔离**：租户是维度定义里一个普通维度，和其他维度走同一套增删改查/条件匹配逻辑；v1 不做基于租户的数据库级隔离。
12. **知识库名称全局唯一，知识点标题库内唯一**：新增/修改时都要做唯一性校验，重复直接报错拒绝，不做自动去重或改名。
13. **写答案强制校验维度已启用**：`coord` 中出现本知识库未启用的维度 key，一律报错拒绝，不做静默忽略。
14. **同一 coord 下 `effective_time` 可以重复，用 `created_at` 兜底排序**：解析"当前版本"时先按 `effective_time` 降序，相同则按 `created_at` 降序，即同一天内多次编辑，最后一次操作胜出。
15. **v1 不支持第三方自带外部 ID 做 upsert，也不支持跨知识库的批量/增量检索**：知识点、答案的主键均由系统生成；第三方需要自行维护"系统 ID ↔ 自己的业务 ID"的映射关系；所有查询/列表接口都限定在单个知识库范围内（详见 §8）。

## 7. 非功能需求

| 项 | 说明 |
|---|---|
| 持久化 | 需要后端服务 + 数据库，替代 demo 的前端 localStorage（**已确认**） |
| 审计 | 答案的创建/编辑/撤回历史天然构成完整留痕；变更留痕页面（知识点级 + 全局）均为对答案历史的**只读派生视图**，不需要额外的日志表，只需保证 `Answer` 表本身不做物理删除、字段齐全（operator/source/revoked_*） |
| 性能 | 知识点/答案量级、查询频率待评估；"按条件组合分组 + 权重回退排序"的解析逻辑需要 §5 提到的索引支撑；知识点列表页在有维度条件时需要对**每个知识点**执行一次解析，量大时需评估是否需要缓存或分页预解析 |
| 可视化 | "立体全景"是纯前端能力，复用标准的知识点+答案查询接口返回的数据在前端计算和渲染，不需要专门的后端接口；实现优先级可以低于核心 CRUD 与查询 |
| 扩展性 | 新增维度不需要改表结构（`coord` 是键值结构）；字段类型集合的增加（如未来要加单选）需要开发支持，且需要重新评估"精确匹配"以外的比较逻辑是否要引入 |
| 外部集成 | 操作人字段的真实来源（外部身份系统）、来源字段的真实来源（如接入第三方数据/AI 生成内容）均尚未接入，预留集成点，不阻塞 v1 上线 |

## 8. v1 不做（Out of scope）

- 单选(枚举)字段类型
- 数值 / 时间维度的区间查询，以及大于/小于/早于/晚于/包含等比较运算符（答案条件与查询条件统一为精确相等匹配）
- 查询条件之间的"或"/分组逻辑
- 一个知识点在**同一条件组合**下有多个并行版本（同 coord 只有一条版本链）
- 角色权限区分（只读 vs 可管理维度定义等）
- 维度与维度之间的依赖/联动规则
- 知识点、答案、维度、知识库的物理删除
- 真正的多租户数据库级隔离（分库分表、强制 tenant 过滤）
- AI 直接问答接口（demo 里的"立体全景""变更留痕"是为未来 AI 追问场景打基础的可视化/审计能力，但 v1 不包含真正的 AI 接口）
- 第三方自带外部 ID 的 create-or-update（幂等 upsert）：知识点/答案的主键均为系统生成，第三方需自行维护映射关系
- 跨知识库的知识点批量检索、增量同步接口：所有知识点相关操作都限定在单个知识库范围内
- 细分错误码体系：v1 对外接口异常统一返回 `code=444` + `msg` 文字说明，不做按错误类型区分的错误码
- 接口鉴权、并发写冲突控制：v1 暂不实现，见 §4.10
