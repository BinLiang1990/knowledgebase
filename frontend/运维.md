# 前端部署 / 运维手册

目标环境：阿里云 CentOS 服务器（跟 [backend/运维.md](../backend/运维.md) 部署的是同一
台），用系统装的 nginx 直接提供静态文件服务，不走 Docker。

> 2026-08 起前端已按《[前端开发规范.md](../前端开发规范.md)》迁移为 Vue 3 + pnpm 技术栈，
> 并改为 **hash 路由 + 相对 base**。对部署的影响见「三、路由与部署路径」——整体上比原来
> 的 React + BrowserRouter 方案更省心：不再需要按子路径改 `base` 重新构建，也不再需要
> nginx 的 `try_files` 回退。

## 为什么前端不需要 Docker

后端要用 Docker/`uv` 是因为 `uvloop`/`httptools` 这类依赖是平台相关的编译产物，直接搬本机
装好的环境过去在 CentOS 上跑不起来。前端 `pnpm build` 产出的是纯静态的
HTML/CSS/JS，不含任何跟操作系统/CPU 架构绑定的二进制，在哪台机器构建出来的都能直接扔给任
何一台 nginx 用——引入 Docker 只是多包一层，没有实际必要，反而会把部署后端时踩过的镜像拉
取 403、CRLF 之类的坑重新引入一遍。

## 一、服务器一次性准备

```bash
yum install -y nginx
systemctl enable --now nginx
```

## 二、构建（在本机做，不需要在服务器上装 Node）

构建产物是平台无关的，直接在你自己的开发机上 `pnpm build` 就行，不需要在 CentOS 服务
器上装 Node/pnpm。

```bash
cd frontend
pnpm install
pnpm build          # vue-tsc 类型检查 + vite build，产出 dist/
# 或 pnpm build:pack  # 同上并打成 dist.tar.gz
```

`.env.production` 已入库（内容是相对接口前缀 `/kb-api`，无秘钥），**正常情况下构建前不需
要再配置任何东西**。只有当目标环境的 nginx 用了别的接口前缀时才需要改
`VITE_APP_BASE_API`——注意它是 `VITE_` 前缀的**编译期**变量，直接内联进产物，改完必须重
新 build 才生效（跟后端 `.env` 那种运行时配置不是一回事）。

## 三、路由与部署路径（hash 路由 + 相对 base）

现在 `vite.config.ts` 生产构建用 `base: './'`（相对路径），路由用 hash 模式
（`createWebHashHistory`，URL 形如 `/kb-web/#/knowledge-bases/1/knowledge-points`）。
两件事因此简化：

1. **dist 可以放在任意路径**：根路径、`/kb-web` 子路径（alias）、换成别的子路径，都不需要
   改配置重新 build——资源引用是相对的，跟着 `index.html` 的位置走。
2. **不需要 `try_files` 回退**：hash 后面的部分不会发给服务器，刷新/直链永远请求的是
   `index.html` 本身，不存在「客户端路由被 nginx 当成文件找不到」的问题。

接口走同域名下的 `/kb-api` 前缀（`.env.production` 的 `VITE_APP_BASE_API`），由 nginx
反向代理到后端——正式环境 `platform-enterprise.yicall.com` 已配好该转发。因为是同域相对
路径，**浏览器侧不再有跨域请求，后端 CORS 白名单与前端部署解耦**（本地 dev 也一样，走
vite 代理）。

## 四、部署代码（首次）

```bash
# 服务器上先建好目标目录（只需要一次）
ssh root@<服务器地址> "mkdir -p /opt/kb-frontend"

# 本机 build 完之后，把 dist/ 的内容传到服务器
rsync -avz --delete dist/ root@<服务器地址>:/opt/kb-frontend/dist/

# 服务器上配置 nginx（首次）
vim /etc/nginx/conf.d/kb-frontend.conf   # 内容见 deploy/nginx.conf.example，改好 server_name/root
nginx -t && systemctl reload nginx
```

> 注意 `dist/` 和 `dist/` 后面都带斜杠——`rsync` 里源路径末尾的 `/` 代表"拷贝这个目录*里面
> 的内容*"，不带斜杠会变成把 `dist` 这个目录本身拷到目标里面，变成
> `/opt/kb-frontend/dist/dist`。用 `scp -r` 也有同样的坑（而且规则更隐晦：取决于目标目录
> 当时是否已存在），所以后面更新流程也统一用 `rsync`，不用 `scp`。

确认：浏览器访问服务器地址，页面能加载；打开 devtools 的 Network 面板确认 `/kb-api/...`
请求正常返回。

## 五、更新代码（日常运维流程）

```bash
cd frontend
pnpm build
rsync -avz --delete dist/ root@<服务器地址>:/opt/kb-frontend/dist/
```

用 `rsync --delete` 而不是 `scp -r` 覆盖，是因为 Vite 每次 build 产出的资源文件名带哈希，
旧的哈希文件不会被新 build 自动覆盖/删除，直接 `scp` 会让 `dist/` 里越堆越多没用的旧文件；
`--delete` 保证服务器上的内容跟本机这次 build 出来的完全一致。

静态文件替换本身不需要 `nginx reload`（nginx 直接读磁盘上的文件，没有进程内缓存），只有改
了 `/etc/nginx/conf.d/kb-frontend.conf` 本身才需要 `nginx -t && systemctl reload nginx`。

## 六、`/kb-api` 反向代理（替代原 CORS 一节）

前端请求统一打到**同域**的 `/kb-api/...`，由 nginx 转发给后端并剥掉前缀。正式环境已配
好；新环境参考：

```nginx
location /kb-api/ {
    proxy_pass http://127.0.0.1:7071/;   # 末尾斜杠 = 剥掉 /kb-api 前缀，端口按实际后端改
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

因为同域，浏览器不发跨域请求，后端的 `CORS_ALLOWED_ORIGINS` 对生产部署不再是必配项（本
地 dev 也走 vite 代理，同理）。只有当确实要从其他域名的页面直接调后端时才需要再碰它。

漏配转发的症状：页面能打开，但接口请求 404/502；`curl http://<域名>/kb-api/knowledge-bases`
直接验证转发是否生效。

## 七、从 Windows 传配置文件到服务器时注意 CRLF

如果 [deploy/nginx.conf.example](deploy/nginx.conf.example) 是在 Windows 上编辑再传上去
的，行尾可能带 `\r`。nginx 对这个通常容忍度比较高，但如果 `nginx -t` 报奇怪的语法错误，先
用 `cat -A /etc/nginx/conf.d/kb-frontend.conf` 看有没有 `^M`，有就
`sed -i 's/\r$//' /etc/nginx/conf.d/kb-frontend.conf` 清一下再 `nginx -t`。
