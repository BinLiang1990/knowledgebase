# 前端部署 / 运维手册

目标环境：阿里云 CentOS 服务器（跟 [backend/运维.md](../backend/运维.md) 部署的是同一
台），用系统装的 nginx 直接提供静态文件服务，不走 Docker。

## 为什么前端不需要 Docker

后端要用 Docker/`uv` 是因为 `uvloop`/`httptools` 这类依赖是平台相关的编译产物，直接搬本机
装好的环境过去在 CentOS 上跑不起来。前端 `npm run build` 产出的是纯静态的
HTML/CSS/JS，不含任何跟操作系统/CPU 架构绑定的二进制，在哪台机器构建出来的都能直接扔给任
何一台 nginx 用——引入 Docker 只是多包一层，没有实际必要，反而会把部署后端时踩过的镜像拉
取 403、CRLF 之类的坑重新引入一遍。

## 一、服务器一次性准备

```bash
yum install -y nginx
systemctl enable --now nginx
```

## 二、构建（在本机做，不需要在服务器上装 Node）

构建产物是平台无关的，直接在你自己的开发机上 `npm run build` 就行，不需要在 CentOS 服务
器上装 Node/npm。

```bash
cd frontend
vim .env.production   # 新建这个文件，填入真实的后端地址，见下一节「为什么」
npm run build          # 产出 dist/
```

`.env.production` 内容示例（跟 [.env.example](.env.example) 格式一样，只是值换成生产地
址）：

```
VITE_API_BASE_URL=https://platform-enterprise.yicall.com/kb-api
```

（正式环境 `platform-enterprise.yicall.com` 已经在仓库里建好了这个文件，不需要每次重新
建；这里列出来是给其他环境/换域名时参考。注意末尾不带斜杠——请求代码是
`` `${API_BASE_URL}${path}` ``，`path` 那边自带开头的 `/`，两边都带斜杠会变成 `//`。）

## 三、为什么后端地址必须在 build 之前就配好

`vite build` 只认 `VITE_` 前缀的变量，而且是**编译期**读取、直接内联进产物里的静态字符
串——跟后端 `.env` 那种"进程启动时读一次"的运行时配置完全不是一回事。如果 build 的时候没
建 `.env.production`，Vite 会退回 [.env.example](.env.example) 里那个开发默认值
`http://127.0.0.1:8000`，线上用户的浏览器请求会打到用户自己电脑的 8000 端口——大概率直接
连不上，页面看起来像是"后端挂了"，其实是构建时配置没传对。`.env.production` 会被
`vite build`（默认 `mode=production`）自动读取，不需要额外传参数，也不需要在服务器上做任
何配置。

## 三点五、子路径部署（`/kb-web`）时的 `base` 配置

正式环境前端不是挂在域名根路径，而是跟其他应用共用同一个 nginx，挂在 `/kb-web` 子路径
下面（nginx 那边配的是 `alias`，见 [deploy/nginx.conf.example](deploy/nginx.conf.example)
的「子路径部署」那段）。这跟 `VITE_API_BASE_URL` 是同一类"编译期内联"的坑，但坑在另一个
地方：Vite 默认假设产物部署在根路径，打包出来的 `index.html` 里 `<script src>`/
`<link href>` 都是 `/assets/xxx.js` 这种根相对路径。部署到 `/kb-web` 子路径下时，浏览器
仍然会去请求根路径的 `/assets/xxx.js`，不会带 `/kb-web` 前缀，落不到 nginx 那个
`location /kb-web` 上，直接 404——页面能打开（`index.html` 本身能通过 `try_files`
兜底），但脚本/样式全部加载失败，看起来像是"资源有问题"。

[vite.config.ts](vite.config.ts) 已经按 `mode` 处理了这个问题：

```ts
base: mode === 'production' ? '/kb-web/' : '/',
```

`npm run build` 默认就是 `mode=production`，不需要额外传参数；本地 `npm run dev` /
`vitest` 不受影响，还是根路径。同理，[src/main.tsx](src/main.tsx) 里
`BrowserRouter` 的 `basename` 也要跟 `base` 对上，否则客户端路由（比如直接访问或刷新
`/kb-web/knowledge-bases/1`）会找不到路由——已经改成从 `import.meta.env.BASE_URL` 读，
不需要手动维护两处。

如果以后子路径本身要改（比如从 `/kb-web` 换成别的路径），`vite.config.ts` 那一行和
nginx 的 `location`/`alias` 得一起改，两边对不上会重新出现同样的 404。

## 四、部署代码（首次）

```bash
# 服务器上先建好目标目录（只需要一次）
ssh root@<服务器地址> "mkdir -p /opt/kb-frontend"

# 本机 build 完之后，把 dist/ 的内容传到服务器
rsync -avz --delete dist/ root@<服务器地址>:/opt/kb-frontend/dist/

# 服务器上配置 nginx（首次）
vim /etc/nginx/conf.d/kb-frontend.conf   # 内容见 deploy/nginx.conf.example，改好 server_name/root
nginx -t && systemctl reload nginx
```

> 注意 `dist/` 和 `dist/` 后面都带斜杠——`rsync` 里源路径末尾的 `/` 代表"拷贝这个目录*里面
> 的内容*"，不带斜杠会变成把 `dist` 这个目录本身拷到目标里面，变成
> `/opt/kb-frontend/dist/dist`。用 `scp -r` 也有同样的坑（而且规则更隐晦：取决于目标目录
> 当时是否已存在），所以后面更新流程也统一用 `rsync`，不用 `scp`。

确认：浏览器访问服务器地址，页面能加载；打开 devtools 的 Network 面板确认接口请求正常（跨
域问题见第六节）。

## 五、更新代码（日常运维流程）

```bash
cd frontend
npm run build
rsync -avz --delete dist/ root@<服务器地址>:/opt/kb-frontend/dist/
```

用 `rsync --delete` 而不是 `scp -r` 覆盖，是因为 Vite 每次 build 产出的资源文件名带哈希，
旧的哈希文件不会被新 build 自动覆盖/删除，直接 `scp` 会让 `dist/` 里越堆越多没用的旧文件；
`--delete` 保证服务器上的内容跟本机这次 build 出来的完全一致。

静态文件替换本身不需要 `nginx reload`（nginx 直接读磁盘上的文件，没有进程内缓存），只有改
了 `/etc/nginx/conf.d/kb-frontend.conf` 本身才需要 `nginx -t && systemctl reload nginx`。

## 六、跨域（CORS）：前端域名要加进后端白名单

前端和后端是两个独立的地址/端口，浏览器发请求是跨域请求。后端用
`CORS_ALLOWED_ORIGINS`（见 [backend/.env.example](../backend/.env.example)）控制允许哪些
来源跨域调用，默认只放了本机开发的 `localhost:5173`。**部署前端后必须把它实际访问的地址
加进后端的 `CORS_ALLOWED_ORIGINS`**（比如 `http://<服务器公网IP或域名>`），改完后端
`.env` 需要重启后端服务才生效。

漏了这一步的症状：页面能打开，但所有接口请求在浏览器 Network 面板里显示失败，报
`CORS policy` 相关的错误，`curl` 直接测接口反而正常（`curl` 不受 CORS 限制，只有浏览器会
拦）。

## 七、从 Windows 传配置文件到服务器时注意 CRLF

如果 [deploy/nginx.conf.example](deploy/nginx.conf.example) 是在 Windows 上编辑再传上去
的，行尾可能带 `\r`。nginx 对这个通常容忍度比较高，但如果 `nginx -t` 报奇怪的语法错误，先
用 `cat -A /etc/nginx/conf.d/kb-frontend.conf` 看有没有 `^M`，有就
`sed -i 's/\r$//' /etc/nginx/conf.d/kb-frontend.conf` 清一下再 `nginx -t`。
